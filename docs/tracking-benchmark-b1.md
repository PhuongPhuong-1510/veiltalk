# Phase B1: controlled avatar benchmark

This phase prepares measurement, not a production optimization. No webcam results have been generated by Codex. `/avatar/motion` defaults remain unchanged. The DEV page uses the same TrackingPipeline, integrated motion profile, processor and renderer. Its existing diagnostic UI adds overhead, so compare A–E within this page; don't treat the previous production-page measurements as an exact before/after baseline.

## Repeatable movement sequence (60s)

Keep head, shoulders, elbows and both hands visible except deliberate occlusions. Use the same sequence/speed in every profile:

1. 0–10s: raise/lower both arms; inspect shoulder stability.
2. 10–20s: bend/straighten elbows, including an arm pointing toward camera.
3. 20–30s: cross hands in front of torso; inspect elbow flips and wrist placement.
4. 30–40s: rotate wrists and open/close fingers.
5. 40–50s: briefly cover an elbow/hand, then uncover; inspect reacquisition.
6. 50–60s: turn head, blink and speak quickly; inspect mouth response.

For A/E explicitly record shoulder jitter, elbow direction/flips, wrist reconstruction, occlusion/reacquire behavior and rapid-mouth response. Do not infer motion quality in B/C/D for missing tasks. Hand coverage is the fraction of tracked outputs, not recall against known visible hands; notes about actual visibility are needed. No automatic quality score is fabricated.

## Reading the exported report

- `overallFps`: accepted callback/frame/model/publish/apply counts divided by actual measurement duration. `videoPresented` uses the full-measurement presented-counter delta divided by elapsed time between its endpoints. Whole-run renderer counter isn't available; `render` is null rather than invented.
- `metrics`: final snapshot contains requested avg/p50/p95, worker round-trip/wait, total process, callback wait, hand coverage (`stateRatio`), fallback/drops, model/delegate/dimensions, motion/apply and cumulative long tasks.
- `snapshots`: bounded series of roughly 2Hz snapshots throughout the measurement. Their FPS is rolling 10s; renderer FPS uses its own existing window. Use these for instability and the 24fps goal, not just a final average. Do not average p95 values or sum parallel branch timings.
- Benchmark timings retain at most 4096 samples per metric, enough for 60s at 30fps. Ordinary Phase A buffers remain 600. Sample counts show unavailable tasks and whether capacity was reached. Total process timing includes diagnostics and bitmap cleanup, with the current frame appearing in the next snapshot. The final distribution can omit that last in-flight frame.
- `handDiagnostics.hintCounts`: absent, fresh (age 0–120ms inclusive), stale (>120ms), invalid age. Ratios use all Hand sampling attempts as denominator; freshness alone doesn't prove valid shoulders/wrists or tracked Pose.
- `handDiagnostics.roiReasonCounts`: actual worker reason: ROI, disabled, no hint, stale hint, invalid plan, ROI miss limit or draw error. No threshold/retry policy changes.
- `handDiagnostics.modes`: actual full-frame/single/combined/split usage, per-mode inference avg/p50/p95, left/right tracked counts and neither tracked count. Counts refer to accepted worker samples mapped to tracking output; dropped worker results are reported separately. Per-mode coverage = tracked count / mode samples. Compare ROI/full-frame timing and losses as observational associations, not proof of causation. Main-thread fallback isn't included in these worker-specific mode aggregates; `stateRatio` still reports overall coverage.
- `qualityNotes`: user-observed motion quality and conditions; metadata records avatar/render settings and browser. Full-frame ratio isn't automatically a failure: no Pose, unreliable Pose or ROI retry limits can intentionally select it.

## Why presented FPS isn't camera sensor FPS

`requestVideoFrameCallback` metadata `presentedFrames` counts video frames submitted for composition. The implementation subtracts presented counters at received pipeline callbacks and divides by their main-thread receipt-time difference. A jump in the counter includes frames for which the pipeline didn't receive/process a callback, so its presented diagnostic can exceed pipeline FPS. Its timestamps don't provide a reliable sensor-capture measurement. Main-thread delay at either endpoint can perturb the estimate; use multiple windows/repeated runs. `track.getSettings().frameRate` describes the configured track, not an observed count.

Reference: https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback

Distinguish sensor/source delivery (not measured), video frames submitted for composition (`videoPresentedFps`), pipeline-received callbacks (`videoCallbackFps`), accepted frames (`pipelineFrameFps`) and published results (`trackingPublishFps`). Renderer FPS is a separate loop.

To investigate 30→15 without modifying the matrix:

1. Repeat A under fixed light, then D under the same light. If presented remains near 30 in D but falls in A, the result supports resource/contention or browser scheduling involvement, not a camera-only explanation. It doesn't identify the exact GPU/thread cause.
2. On `/dev/tracking`, select **Camera only**, GPU and 1280×720. Measure its video FPS with the existing button for stationary and identical motion, multiple 10s windows. This is a camera/browser diagnostic, never the main avatar benchmark baseline. If it drops here too, inference isn't necessary for the drop.
3. Repeat that camera-only diagnostic with stronger constant front lighting; if available, separately test shorter/manual exposure in the webcam's own settings. Label it as a changed-condition diagnostic and restore settings before A–E. A reproducible light/exposure response supports that cause; it does not prove defective camera hardware.
4. If camera-only stays stable but avatar video drops, optionally repeat A while renderer is stopped, using the Phase A panel for this separate diagnostic (the B1 runner requires renderer ON). Compare presented FPS, inference, long tasks and callback wait. Then restore renderer for the matrix.
5. If needed, capture a short browser Performance trace with the same scenario to examine main-thread long tasks and rendering. Profiling adds overhead; don't mix trace runs with matrix baseline. A separate capture app with actual frame timestamps can help check source delivery after closing browser capture. Visual smoothness alone isn't an FPS measurement.

## Existing staggered scheduling, not changed

At each accepted frame, full-rate requests every enabled task. Staggered requests Hands/Pose only if `startedAt - lastSampleMs >= intervalMs`; Face still runs every accepted frame. Hands/Pose last-sample time is the frame-start clock, not inference completion. A late/dropped Hand sample still advances its current sampling clock according to the existing path.

At ~10fps with ~100ms gaps, 66.7ms is already exceeded each time, so staggered need not skip any Pose. For regular 100ms gaps, an interval just over 100ms would generally select every second frame (~5Hz); ~200ms boundary behavior depends on jitter. There is no independent task clock, catch-up queue or backlog. Decreasing processing cost changes the accepted-frame gaps and therefore the achieved per-task frequency. Setting an interval does not guarantee that rate.

For B2, first use A/C/E measurements to quantify how much removing/lightening Pose changes both the main branch and Hand ROI. A possible future controlled-rate design is a per-task next-due deadline that skips missed deadlines, processes only the latest available frame, and reports achieved task Hz/age. At accepted-frame throughput below the requested task rate, task Hz cannot exceed accepted frames. This is a proposal only; no new scheduler, intervals, sampling or model defaults have been implemented.
